# 产品简报: 文章AI解读功能

## 0. 项目章程

- **商业目标**：为论坛文章提供AI辅助精准解读，帮助用户理解复杂/专业内容，提升阅读深度和用户留存。现在做是因为AI大模型API成本大幅下降且标准化（OpenAI兼容接口），可在不显著增加成本的前提下提供差异化服务。
- **项目范围（一句话）**：用户在文章详情页选中任意文本段落，系统调用AI大模型基于原文进行严格解读，流式返回结果并Markdown渲染展示。
- **明确不在范围内**：对话模式、自动摘要整篇文章、解读历史记录、管理后台配置面板、前端模型选择器。
- **与现有系统的关系**：复用现有AI策略模式架构（ChatFacade + ChatService），扩展AISourceEnum和配置体系，新增REST API（非WebSocket，因解读是单次请求-回复场景），前端复用md-editor-v3组件做Markdown渲染。
- **关键干系人**：
  - 终端用户（论坛读者）— 期望快速准确理解难懂内容
  - 运营人员 — 期望提升用户停留时间和活跃度
  - 开发者 — 期望可扩展的模型配置体系
- **约束**：
  - 技术栈：SpringBoot 3 + Vue 3 + Element Plus + MyBatis-Plus
  - 必须支持流式响应
  - 固定系统提示词硬编码于后端
  - 复用现有元素：ChatFacade门面、STOMP/WebSocket架构、md-editor-v3渲染组件
- **关键假设**：
  - 主流AI厂商（DeepSeek、通义千问、Kimi等）均提供OpenAI兼容API接口
  - OpenAI兼容API的流式响应格式统一（SSE `data: [DONE]` 终止符）
  - 用户对AI解读有真实需求（需上线后数据验证）
- **项目风险**：
  - 部分AI厂商API不稳定或限流 → 缓解：多模型自动降级fallback策略
  - 流式响应中断导致用户体验差 → 缓解：30秒超时+重试+降级为同步返回
  - AI解读质量不佳导致用户不信任 → 缓解：提示词严格约束"不准脱离原文、不准编造"
  - API费用超出预期 → 缓解：每位用户每日50次调用上限

## 1. 产品定位

**"文章专属解读助手"** — 基于AI大模型的文章片段精准解读工具。

- 用户选中文章中的任意文本 → 一键触发AI解读 → 获得基于原文的专业解读
- 严格基于原文，不编造、不杜撰，保障解读可信度
- 定位为"辅助阅读理解"工具，非"知识问答"或"对话聊天"

## 2. 用户画像

| 角色 | 场景 | 痛点 | 期望 |
|------|------|------|------|
| 技术学习者 | 阅读深度技术文章 | 遇到专业术语/复杂逻辑难以理解 | 快速获得通俗易懂的解释 |
| 论坛潜水用户 | 浏览社区热帖 | 文章较长，不想逐字阅读 | 选中感兴趣段落获取解读 |
| 内容创作者 | 参考他人文章 | 想快速理解某段落的要点 | 精准、不跑偏的解读 |

## 3. 功能范围 (MoSCoW)

### Must Have
- [x] 后端统一OpenAI兼容API调用层，支持多模型配置
- [x] 至少支持3个主流模型提供商（DeepSeek、Kimi、通义千问）+ 保留现有ChatGPT/讯飞
- [x] 文章解读专用REST API端点
- [x] 固定系统提示词硬编码于后端（不可配置，不可通过API修改）
- [x] 前端文章详情页文本选中 → 浮动"AI解读"按钮
- [x] 流式返回解读结果 + Markdown渲染
- [x] 多模型自动降级fallback

### Should Have
- [ ] YAML配置文件支持动态添加新模型提供商
- [ ] 解读结果一键复制
- [ ] 完整的加载/错误/超时/空结果状态处理
- [ ] 用户日调用限制

### Could Have
- [ ] 解读结果反馈（满意/不满意）
- [ ] 同一段落的多次解读对比

### Won't Have (v1)
- [ ] 对话式追问模式
- [ ] 一键全文自动摘要
- [ ] 用户个人解读历史记录
- [ ] 管理后台模型配置面板
- [ ] 前端模型选择器

## 4. 成功指标

| 指标 | 目标 | 衡量方式 |
|------|------|----------|
| API响应性能 | P95 < 5秒 | 服务端日志统计 |
| 功能使用率 | 上线1周后10%+文章浏览用户触发至少1次 | 埋点统计 |
| 错误率 | < 1% | 服务端监控 |
| 用户满意度 | 正面反馈 > 70% | "满意"按钮点击统计 |
| 模型可用性 | 99%+ 时间至少有1个模型可用 | 健康检查监控 |

## 5. 产品风险

| 风险 | 影响 | 概率 | 缓解策略 |
|------|------|------|----------|
| AI API费用超预算 | 运营成本上升 | 中 | 用户日限额50次；选择性价比高的模型做默认 |
| 解读质量不稳定 | 用户体验差 | 中 | 固定系统提示词约束；建立反馈闭环优化提示词 |
| 流式响应兼容性问题 | 部分浏览器异常 | 低 | 降级方案：流式失败则同步返回完整结果 |
| 特定模型厂商API变更 | 服务中断 | 低 | 多模型fallback；关键日志告警 |
