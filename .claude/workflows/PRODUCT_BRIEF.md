# 产品摘要文档（PRODUCT BRIEF）

## 项目章程：私信会话清除功能

### 商业目标

为派编程社区平台的私信功能增加用户侧会话清除能力，解决用户在私信列表中存在大量无用/过期会话时的管理困扰。该功能属于基础体验优化，虽不直接产生拉新效果，但能提升用户对私信功能的掌控感，降低认知负担，间接提升私信功能使用率和用户留存。

### 问题定义

**当前痛点：**
- 用户在私信列表中长期积累大量会话，无法清理
- 某些一次性的会话（如活动通知、临时交流）长期占据会话列表空间
- 用户缺乏对自己私信空间的管理控制权

**用户需求（JTBD）：**
- 当用户不再需要查看与某人的历史私信记录时，希望能一键清除该会话，使会话列表保持整洁
- 清除不影响对方，对方仍能看到完整历史记录

## 约束与假设

### 约束

| 约束项 | 说明 |
|--------|------|
| 数据完整性 | 消息数据不得物理删除，保留完整的会话历史用于合规和审计 |
| 单方面操作 | 清除操作仅影响操作者的视图，不得影响对方或其他会话成员 |
| 技术栈约束 | 必须使用现有技术栈：Spring Boot 3 + MyBatis-Plus + MySQL + Liquibase；前端 Vue 3 + Element Plus + TypeScript + Pinia |
| 数据库变更 | 必须通过 Liquibase changelog 进行 DDL 变更，不使用手动 SQL |
| API 兼容 | 新增 API 端点不影响已有私信 API 的行为 |

### 假设

| 假设项 | 说明 | 风险等级 |
|--------|------|----------|
| A1 | 现有的 `conversation_member.is_deleted` 字段的设计意图与本需求一致，可用于隐藏已清除的会话 | 低 |
| A2 | 在 `conversation_member` 表新增 `cleared_at` 字段对现有功能无影响（NULL 默认值 + 索引） | 低 |
| A3 | `getOrCreatePrivateConversation` 中删除方成员记录的重新激活逻辑不会引入并发问题（synchronized 已存在） | 低 |
| A4 | 对方发送新消息后重新激活会话的行为符合用户预期 | 低 |

## 技术方案概要

### 数据模型变更

在 `conversation_member` 表新增一个字段：

```
cleared_at  DATETIME  NULL  COMMENT '用户清除该会话的时间点(用于过滤消息, NULL表示从未清除)'
```

现有的 `is_deleted` 字段语义不变：`0` = 可见，`1` = 已清除（隐藏）。

### 清除操作流程

```
用户点击清除 → 确认弹窗 → 后端 API 调用 → 
  SET conversation_member.is_deleted = 1
  SET conversation_member.cleared_at = NOW()
  SET conversation_member.unread_count = 0
  → 前端返回会话列表页
```

### 新消息重新激活流程

```
对方发送消息 → send() → getOrCreatePrivateConversation() 找到已有会话（忽略接收方 is_deleted 状态）
  → 插入消息
  → 如果接收方 member.is_deleted = 1：
      SET is_deleted = 0（激活，但保留 cleared_at）
  → WebSocket 推送 → 接收方看到会话重新出现，只能看到 cleared_at 之后的消息
```

### 消息加载过滤

查询历史消息时，如果当前用户的 `cleared_at` 不为 NULL，则仅返回 `create_time > cleared_at` 的消息：

```sql
-- 伪代码
SELECT m.* FROM message m
JOIN conversation_member cm ON m.conversation_id = cm.conversation_id AND cm.user_id = ?
WHERE m.conversation_id = ?
  AND (cm.cleared_at IS NULL OR m.create_time > cm.cleared_at)
ORDER BY m.create_time DESC
```

### API 端点

| 方法 | 路径 | 说明 |
|------|------|------|
| `DELETE` | `/api/msg/conversations/{conversationId}` | 清除当前用户在该会话的历史记录 |

### 前端变更点

| 文件 | 变更 |
|------|------|
| `MessageHeader.vue` | 新增清除按钮（三点菜单或独立图标按钮） |
| `ConversationView.vue` | 接入清除逻辑，清除后返回列表 |
| `MessageRequests.ts` | 新增 `clearConversation()` API 调用 |
| `URL.ts` | 新增 `MSG_CLEAR_CONVERSATION_URL` 路径常量 |
| `message.ts` (store) | 新增 `removeConversation()` action |

## 用户故事 & 验收条件

### US-1: 清除会话历史记录

**作为** 社区用户
**我想要** 在私信聊天界面中一键清除与某用户的所有历史消息
**以便于** 保持我的会话列表整洁，不再看到不需要的历史消息

**验收条件：**

1. 在聊天界面顶部（MessageHeader 区域）有一个"清除记录"操作入口（三点菜单按钮或文字按钮）
2. 点击"清除记录"后，弹出 Element Plus 确认对话框，文案：「清除后，你将看不到该会话的所有历史消息。对方不受影响。此操作不可撤销。」
3. 确认后，调用后端 API 完成清除，自动跳转回会话列表页（`/messages`）
4. 取消后，停留在当前页面，不做任何操作
5. 清除后，该会话从会话列表中消失
6. 对方用户的会话列表和聊天记录不受任何影响

### US-2: 清除后对方发来新消息时重新激活会话

**作为** 已清除某会话的用户
**我想要** 当对方再次发来消息时，该会话自动重新出现在我的会话列表中
**以便于** 我仍能收到来自该用户的新消息

**验收条件：**

1. 清除会话后，对方发送新消息，该会话重新出现在当前用户的会话列表中
2. 重新出现的会话仅显示清除时间点之后的消息，不显示清除前的历史消息
3. 对方仍能看到所有消息（包括清除前和清除后的），不受影响
4. 新消息会产生未读计数（红点/数字徽标）

### US-3: 清除操作不可撤销

**作为** 系统设计者
**我想要** 消除操作是不可逆的（产品决策）
**以便于** 简化实现复杂度，避免引入"回收站"机制

**验收条件：**

1. 确认对话框中明确提示「此操作不可撤销」
2. 清除完成后，不提供任何"撤销"或"恢复"入口
3. 如果用户重新发起与新消息的会话（通过点击会话列表），看到的仍然只有清除后的新消息

## 风险评估与缓解策略

| 风险 | 严重程度 | 可能性 | 缓解策略 |
|------|----------|--------|----------|
| R1: 清除后对方发消息创建了重复会话 | 高 | 中 | 修改 `getOrCreatePrivateConversation` 方法，查找已有会话时忽略目标用户的 `is_deleted` 状态；发送消息时自动激活接收方的成员记录 |
| R2: 用户在清除后立刻收到新消息，cleared_at 与消息 create_time 时序竞争 | 中 | 低 | 清除操作与消息发送受同一事务保护（已存在的 synchronized + @Transactional），时序窗口极小；即使出现边界情况，新消息会显示出来，不影响核心功能 |
| R3: 用户误操作清除重要会话 | 中 | 中 | 必须通过确认弹窗二次确认；弹窗明确文案提示不可撤销；UI 按钮不放在容易误触的位置 |
| R4: 数据库字段新增影响现有查询性能 | 低 | 低 | `cleared_at` 仅在加载消息时作为过滤条件使用，利用现有的 `idx_msg_conversation_time` 索引；字段本身为 NULL 时不影响查询 |
| R5: 前端未登录状态或无权限访问清除 API | 低 | 低 | API 由 `@Permission(role = UserRole.LOGIN)` 保护；前端入口仅在已登录状态下渲染 |

## 附录：关键设计决策

### 决策 1: 新增 `cleared_at` 字段 vs 复用 `last_read_message_id`

**选择**：新增 `cleared_at` 字段。

**理由**：
- `last_read_message_id` 的语义是"标记已读位置"，用于计算未读数，清除后仍需保留已读状态
- `cleared_at` 语义清晰，专门表示"用户清除时间"，与已读逻辑解耦
- 未来如果有"按时间点清除"或"部分清除"需求，`cleared_at` 可直接复用

### 决策 2: 清除后不再提供撤销

**选择**：不提供撤销/回收站机制。

**理由**：
- 保持产品简洁，避免回收站增加的 UI 复杂度
- 用户已有二次确认（确认弹窗），误操作风险已降低
- 与微信等主流 IM 产品的"清空聊天记录"行为一致

### 决策 3: 不在会话列表项上提供快速清除入口（V1）

**选择**：仅从聊天界面内部提供清除入口。

**理由**：
- 减少会话列表的视觉复杂度
- 用户在查看会话详情后才做出清除决策，决策质量更高
- 滑动删除/右键删除作为 Could Have 后续迭代

### 决策 4: `is_deleted` 字段语义保持不变

**选择**：`conversation_member.is_deleted` 字段继续表示"用户侧是否已删除该会话"。

**理由**：
- 当前查询逻辑（`listByUserId` 筛选 `is_deleted = 0`）可直接复用
- 清除后 `is_deleted = 1` 自然地从列表中隐藏
- 对方发新消息时设置 `is_deleted = 0` 自然地在列表中重新显现
